# AI Framework Instructions: @hari/playwright-core

This document serves as the comprehensive source of truth for any AI agent interacting with, extending, or maintaining the `@hari/playwright-core` enterprise test automation framework.

## 1. Framework Identity & Purpose
`@hari/playwright-core` is a centralized, modular test automation framework built on top of native Playwright. 
**Primary Goal:** Standardize enterprise testing by providing instant scaffolding, pre-built API clients, strict Page Object Model (POM) patterns, unified configurations (local + cloud), and zero-config Allure reporting.

## 2. Core Architecture & Modules
Whenever an AI generates or modifies tests utilizing this framework, it MUST leverage the provided core modules rather than native Playwright alternatives.

### A. The Custom `test` Fixture (`baseFixtures.ts`)
- **Rule:** Never import `test` or `expect` from `@playwright/test` directly in the test spec if testing a scaffolded project. Always import from `@hari/playwright-core` or the local base fixture that extends it.
- **Capabilities:** Injects `apiClient` (custom API wrapper) and `envConfig` (strongly typed environment variables).

### B. Enterprise API Client (`ApiClient.ts`)
- **Rule:** Never use native `fetch` or raw Playwright `request`. Always use the injected `apiClient` fixture.
- **Features:**
  - Auto-injects Base URLs and Bearer tokens based on `envConfig`.
  - Implements automatic exponential backoff retries for 5xx errors.
  - Automatically attaches requests and responses to the Allure report via `test.step()` and `test.info().attach()`.

### C. Environment Configuration (`envConfig.ts`)
- **Rule:** No hardcoded credentials, URLs, or environment-specific strings.
- **Features:** Parses `.env` securely. Exposes environments explicitly.

### D. Smart Runners (`runConfig.ts` & `browserStack.ts`)
- **Rule:** Use `withRunConfig()` to wrap native Playwright configuration. It allows `runconfig.json` overrides without modifying `playwright.config.ts`.
- **Dynamic Workers:** The framework supports dynamic worker scaling (e.g., `"workers": "50%"`) adapting to the host CPU cores.

## 3. Supported Testing Paradigms
The framework supports three runners via its CLI scaffolding. AI agents should adapt based on the project's chosen paradigm:
1. **Native Playwright (Non-BDD):** Standard `.spec.ts` files utilizing POM.
2. **Playwright BDD:** Uses `playwright-bdd` (Gherkin compiled to Playwright specs).
3. **Cucumber BDD:** Uses `@cucumber/cucumber`.

## 4. AI Development Guidelines & Best Practices
When generating code for this framework or its consumers:
- **Strict POM:** Separate locators and actions into distinct Page Object classes. Specs should only contain orchestrations and assertions.
- **Allure Reporting:** Rely on the framework's automatic attachments. Do not manually write `allure.logStep` unless extending custom behaviors.
- **Error Handling:** Let the `ApiClient` handle API retries. Do not wrap API calls in custom try-catch blocks unless expecting a specific logical failure.
- **No Native Playwright Test Imports:** `import { test, expect } from '@hari/playwright-core';` is mandatory.

## 5. Skills and Integrations
- **CI/CD:** Always respect the `workers` and `retries` logic configured via `withRunConfig` when adapting for CI.
- **BrowserStack:** Recognize that setting `USE_BROWSERSTACK=true` intercepts Playwright's local browser initialization and pipes it to the cloud seamlessly.

Use this context to accurately scaffold, debug, and expand the framework or projects generated by it.
